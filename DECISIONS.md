# Slideshow: decisions

2026-10-30 — One self-contained HTML file that holds images as in-memory object URLs: no server, no dependencies, no network, no file writes. Only the settings go to localStorage. Reason: Brett asked for an app that makes no copies or other files needing cleanup; a page holding references to the original files meets that exactly.

2026-10-30 — The image sequence isn't saved. Reason: saving it means writing state somewhere. Chrome's File System Access API is the follow-up if a sequence ever needs to survive a reload.

2026-10-30 — Claude fixed seven things after round 2 instead of running a third qwen round. Fixes: (1) `transition()` read which layer was front and which back before finishing the transition in flight, which swaps them, so pressing an arrow mid-transition would have loaded the new image into the visible layer; (2) the first slide now goes through `decode()` and is skipped if it can't be shown; (3) when an undecodable image is the last one, the show wraps to the start if looping instead of stepping back; (4) files from the pickers are added in natural name order, like dropped files; (5) ← at "End" steps back instead of reloading the last image; (6) UI copy: em-dashes removed, and "nothing saved" changed because the settings are saved; (7) leaving a show clears both image layers, so a second show can't open on the first one's last frame.

2026-10-30 — Supersedes "the image sequence isn't saved": Brett chose both safeguards for a lost arrangement. (a) A `beforeunload` warning while images are loaded. (b) The order is remembered in localStorage as file identity keys (name|size|lastModified), never file data; after the same files are added again, a bar offers to restore it. While that offer is pending the saved order isn't overwritten; Dismiss or any arrangement action (drag, sort, remove, clear) replaces it. Reason: a side agent pointed out that one accidental reload threw away a long arrangement. Renaming files was rejected because it alters the originals, and a saved order file because it breaks the no-files rule. File names now sit in browser storage, which the UI copy and README say.

2026-10-30 — Restore matching falls back to the file name: exact identity first, then by name only where the name is unique among the still-unmatched saved files and the still-unmatched current ones. The bar reports how many were matched by name. Reason: Brett had approved remembering the order "by filename", but the implementation matched name|size|lastModified, so edited or re-exported photos silently dropped out of the restore offer (raised by a side agent). Unambiguous fallback rather than name-only matching, so two different files sharing a name aren't guessed. Saved format unchanged.
